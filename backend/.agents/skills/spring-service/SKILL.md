# Spring 도메인 서비스 작성

## 관련 스킬 참조

- 이 스킬의 호출 이름은 `$spring-service`다.
- DAO·XML 매퍼 생성·수정이 필요한 범위에서는 [mybatis-dao](../mybatis-dao/SKILL.md)를 읽어 메서드와 DB 매핑을 맞춘다.
- 컨트롤러 호출부나 HTTP 요청·응답 변경이 필요한 범위에서는 [spring-controller](../spring-controller/SKILL.md)를 읽는다.
- 회원아이디 검증 규칙 자체를 적용·검토하는 작업이면 [member-id-validation](../member-id-validation/SKILL.md)을 읽는다. 이를 이유로 서비스에 HTTP 바인딩이나 중복된 DTO 검증을 추가하지 않는다.
- 관련 스킬은 필요한 작업에만 적용하며, 사용자 지시와 기존 호출 계약을 우선한다.

## 참조와 범위

참조 파일은 `src/main/java/com/mycompany/demo/database/service/MemberService.java`다. 연결된 `database/dao/MemberDao.java`, `database/dto/Pager.java`, 호출 컨트롤러도 함께 확인한다. 프로젝트나 경로가 다르면 같은 역할의 코드를 찾아 실제 패키지·도메인에 맞춘다.

참조에서 일반화할 구조는 `@Service`, final DAO 필드와 생성자 주입, Entity 입출력, DAO 호출을 통한 CRUD, 검색 건수 및 페이지 목록 조회다. 회원가입이라는 이름이나 문자열 회원 ID를 모든 도메인에 복사하지 않는다. 참조의 사용하지 않는 import·불균일한 들여쓰기를 규칙으로 만들지 않는다.

서비스는 업무 처리와 DAO 호출을 담당한다. HTTP 바인딩 어노테이션, Request/Response DTO, HTTP 응답용 Map·메시지는 컨트롤러 경계에 둔다. 서비스 작성만 요청받았으면 무관한 엔드포인트·스키마를 변경하거나 실제 DB 데이터를 변경하지 않는다.

## 구조와 의존성

- 해당 도메인 이름의 `*Service` 클래스를 만들고 `@Service`를 붙인다. 인터페이스/구현 분리는 프로젝트가 이미 사용하거나 필요할 때 적용한다. 모든 서비스에 불필요한 인터페이스를 추가하지 않는다.
- 필요한 DAO·협력 서비스만 `private final` 필드로 선언하고 생성자 주입한다. 명시적 생성자를 기본 참조로 삼되, 기존 프로젝트가 Lombok `@RequiredArgsConstructor`를 쓰면 그 방식을 유지할 수 있다. 같은 생성자를 두 방식으로 중복 생성하지 않는다.
- 생성자명과 클래스명이 일치하고 모든 final 의존성을 초기화해야 한다. 서비스가 자기 자신을 주입하거나 협력 서비스끼리 순환 의존하지 않도록 확인한다.
- 패키지가 달라도 같은 단순 클래스명은 기본 빈 이름이 충돌할 수 있다. 같은 이름의 서비스가 있으면 구별되는 이름을 정하고 기존 주입부도 확인한다. `@Qualifier`는 실제로 같은 타입의 후보가 여러 개일 때 적용한다.
- `@Slf4j`는 로그가 필요할 때 사용한다. 비밀번호·토큰이나 이를 포함한 Entity 전체를 로그로 출력하지 않는다.

## 메서드 계약

메서드 계약은 다음과 같다. insert·update·delete에 해당하는 서비스 메서드는 이름이 join, register 등이어도 반드시 int를 반환한다. 참조 코드가 이 규칙과 다르면 해당 작업 범위에서 이 규칙에 맞춘다. 메서드명은 작업과 도메인을 표현하며, 존재하는 DAO 메서드의 이름·인자·반환형과 연결한다.

| 작업 | MemberService 참조 | 일반화할 의미 |
| --- | --- | --- |
| 단건 조회 | `Member getMember(String memberId)` | 키로 DAO를 조회하고 Entity 반환 |
| 저장 | `int join(Member member)` | Entity를 DAO에 전달해 저장하고 영향받은 행 수 반환 |
| 수정 | `int updateMember(Member member)` | DAO가 수정한 행 수 반환 |
| 삭제 | `int deleteMember(String memberId)` | DAO가 삭제한 행 수 반환 |
| 검색 건수 | `int pagingTotalRows(Map<String, Object> where)` | 조건에 맞는 전체 건수 반환 |
| 페이지 목록 | `List<Member> listMember(Pager pager, Map<String, Object> where)` | 조건에 맞는 해당 페이지의 Entity 목록 반환 |

- 예시는 회원 도메인에 한정된다. `Product`, `Seller`, `Orders` 등 실제 Entity와 `String`, `Long`, 복합키 등 실제 키 타입을 사용한다.
- 새 기능에 필요한 메서드만 작성한다. 구현되지 않은 메서드에 무조건 성공값을 반환하거나, 목록 조회를 실제로 실행하지 않고 빈 목록을 반환하는 식으로 완성된 것처럼 만들지 않는다.
- 저장·수정·삭제 서비스의 반환형은 모두 `int`로 통일한다. DAO의 실행 결과를 반환하며, 호출부에서 결과를 사용하지 않아도 void·boolean·Entity·Map으로 바꾸지 않는다.
- 반환하는 int는 영향받은 행 수다. 일반적인 단건 작업에서 1은 처리됨, 0은 처리된 행 없음이다. DB 예외를 숨기고 일괄 성공으로 바꾸지 않는다. 여러 쓰기 작업이면 어떤 대상 작업의 행 수인지 계약을 명시하고, 서로 다른 테이블의 행 수를 무조건 더하지 않는다.
- 생성된 PK는 등록 Entity의 ID 필드 등 기존 키 반환 방식으로 전달하며 int 반환값을 PK로 해석하지 않는다. 저장·수정 후 응답 데이터가 필요하면 별도의 조회 메서드로 Entity를 조회한다. 조회·목록 메서드의 Entity·List 반환형은 그대로 유지한다.
- 컨트롤러에서 Request DTO를 Entity로 변환해 전달하는 규칙을 적용할 때 서비스도 Entity를 받도록 맞춘다. 참조의 단순 ID·검색 Map 계약은 기존 호출부와 직접 서비스 호출에 사용할 수 있지만, 이를 이유로 컨트롤러 DTO를 서비스에 전달하지 않는다. 필요한 ID는 서비스에서 Entity로부터 추출해 DAO에 넘긴다.
- 현재 작업이 기존 서비스 계약 보존이라면 단순 ID나 검색 Map 인자를 일괄 리팩터링하지 않는다. 사용자가 조건 없는 조회를 요청했다면 불필요한 검색 인자를 강제하지 않고 DAO에 null 또는 빈 조건을 전달한다.
- 서비스 시그니처를 바꾸면 실제 호출부를 검색해 메서드명·대소문자·인자 수·타입·반환값을 함께 검증한다. 예를 들어 `update`와 `updateMember`, `void`와 `int`를 혼용하지 않는다.

## 업무 처리와 데이터 보존

- 단순 CRUD는 DAO 위임만으로 충분할 수 있다. 불필요한 업무 규칙이나 예외 계층을 만들어 작업 범위를 넓히지 않는다.
- 단건 조회 결과가 없는 경우의 계약은 기존 정책을 따른다. null을 반환하는 구조라면 호출자가 부재를 처리하도록 연결하며, null Entity의 getter를 호출하지 않는다. 컨트롤러의 404 같은 HTTP 처리와 서비스의 도메인 처리를 구분한다.
- 일부 필드만 수정하는 요청에서는 수정 대상 필드를 확인한다. DAO SQL이 전체 컬럼을 갱신한다면 기존 Entity를 조회해 허용한 값만 변경하거나, 적합한 부분 수정 SQL을 사용하여 누락된 값이 이름·가입일 등을 null로 덮어쓰지 않도록 한다.
- PK·서버 생성 시간 등 변경하면 안 되는 값과 업무 규칙을 확인한다. 요청에 없던 검증 조건, 비밀번호 형식, 삭제 정책을 임의로 추가하지 않는다.
- FK·UNIQUE 위반 같은 DB 오류를 무조건 삼키지 않는다. 업무상 필요한 도메인 오류 변환은 프로젝트의 기존 처리 정책에 맞춘다.

## 페이징과 검색

- 건수와 목록은 동일한 검색 조건을 DAO에 전달한다. 참조의 `where == null`은 전체 행 검색을 뜻하며, 실제 매퍼가 이를 지원하는지 확인한다.
- 기존 Pager를 재사용한다. `totalRows`는 현재 페이지 행 수가 아니라 검색 대상 전체 행 수다. 정렬·LIMIT/OFFSET은 DAO 매퍼에서 처리하고 서비스가 전체 행을 읽어 잘라내지 않는다.
- 페이지 번호와 크기의 유효성은 기존 입력 검증 위치에서 처리한다. 서비스가 직접 호출되는 경우에도 음수 OFFSET이 발생하지 않도록 계약을 확인한다.
- 목록 결과는 Entity 목록을 반환하고, 컨트롤러가 각 항목을 Response DTO로 변환한다. HTTP 응답의 pager/data 봉투를 서비스에서 만들지 않는다.

## 트랜잭션

- 업무 단위의 여러 쓰기, 조회 후 변경처럼 함께 성공·실패해야 하는 작업에는 서비스의 public 메서드에 `@Transactional`을 적용한다. 하나의 DAO 호출을 위임하는 모든 메서드에 기계적으로 붙이지 않는다.
- 단순 조회는 필요하면 `@Transactional(readOnly = true)`를 사용하되, import가 있거나 readOnly가 붙었다는 사실만으로 원자성·일관성이 검증됐다고 판단하지 않는다. 실제 격리 수준과 호출 경계를 확인한다.
- 여러 DAO가 관여하는 업무는 외부에서 호출되는 서비스 메서드에 트랜잭션 경계를 둔다. 동일 객체 내부 호출의 프록시 적용 여부와 체크 예외 롤백 요구를 고려한다.
- 트랜잭션 안에서 예외를 무조건 잡고 성공을 반환하지 않는다. `rollbackFor` 등의 추가 설정은 실제 요구가 있을 때만 사용한다.

## 검증과 보고

- Service 생성자·빈 등록·DAO 메서드·Entity 타입·컨트롤러 호출·XML 매핑의 연결을 대조한다. 없는 DAO 메서드를 호출하지 않는다.
- 기존 wrapper로 전체 빌드를 실행해 메인 코드뿐 아니라 테스트 컴파일과 기존 테스트도 확인한다. Gradle은 `gradlew.bat build`, Maven은 프로젝트의 기존 빌드 명령을 사용한다.
- 기존 관련 테스트가 있으면 실행한다. 업무 규칙이나 다단계 처리가 달라지면 필요한 경우에만 Mockito·롤백 가능한 통합 테스트 등으로 정상 처리, 대상 없음, 변경 보존, 실패 처리를 검증한다. 단순 위임을 그대로 복사한 테스트를 무조건 추가하지 않는다.
- Java 컴파일·컨텍스트 로딩·실제 SQL 실행을 구분해 보고한다. 실행하지 않은 DB 처리를 검증했다고 말하지 않는다. 관계없는 빌드 오류는 위치와 함께 분리해 보고한다.
