# 회원아이디 검증

회원가입 또는 회원정보 입력 모델의 회원아이디 필드에 아래 규칙을 적용한다. 특정 패키지, 클래스명, 필드명에 의존하지 않는다.

## 대상 확인

- 사용자가 지정한 클래스와 필드를 우선한다. 지정하지 않았다면 요청 처리 코드와 DTO를 확인해 `mid`, `memberId`, `username`, `loginId` 등 실제 로그인 아이디를 받는 문자열 필드를 찾는다. 이름만 보고 데이터베이스 기본키나 이메일 필드를 선택하지 않는다.
- 대상이 여러 개이고 코드 흐름으로 구분할 수 없다면 적용 대상을 질문한다.
- 기존 검증 어노테이션, validation 의존성, 메시지 관리 방식을 확인한다. 프로젝트에서 사용하는 `jakarta.validation` 또는 `javax.validation` 네임스페이스에 맞추고 둘을 혼용하지 않는다.
- 사용자가 별도 규칙을 지정하면 그 요청을 우선한다. 다른 필드나 컨트롤러는 요청 범위에 포함된 경우에만 변경한다.

## 검증 규칙

- 필수 입력: null, 빈 문자열, 공백만 있는 문자열을 허용하지 않는다.
- 길이: 최소 5자, 최대 20자이다.
- 첫 글자: 영문 소문자 또는 대문자여야 한다.
- 영문 대문자 `A-Z`를 반드시 1자 이상 포함한다.
- 전체 문자열에는 영문자 `a-z`, `A-Z`, 숫자 `0-9`, 특수기호 `!`, `_`만 허용한다.
- 숫자와 특수기호는 사용할 수 있지만 반드시 포함할 필요는 없다. 소문자도 필수는 아니다.

## 적용 코드

다음은 Jakarta Bean Validation을 사용하는 예시다. `jakarta.validation.constraints.NotBlank`, `Size`, `Pattern`을 import한다. 기존 프로젝트가 `javax.validation`을 사용한다면 해당 네임스페이스를 따른다. 길이는 `@Size`로 검사하고 문자 구성은 `@Pattern`으로 검사한다.

예시의 `memberId`는 실제 필드명으로 바꾼다. 기존 어노테이션과 중복되거나 충돌하지 않도록 통합하고, 오류 메시지는 프로젝트의 언어와 메시지 키 사용 방식에 맞춰 실제 규칙을 설명한다.

```java
@NotBlank(message = "id는 필수 입력 항목입니다.")
@Size(min = 5, max = 20, message = "id는 5자 이상 20자 이하여야 합니다.")
@Pattern(
    regexp = "(?=.*[A-Z])[a-zA-Z][a-zA-Z0-9!_]*",
    message = "id는 영문자로 시작하고 대문자를 1개 이상 포함해야 하며, 영문자, 숫자, !, _만 사용할 수 있습니다."
)
private String memberId;
```

숫자와 특수기호의 **허용**과 **필수 포함**을 구분한다. 위 규칙에서는 숫자와 특수기호가 선택 사항이므로 오류 메시지에서도 필수라고 안내하지 않는다.

## 확인 예시

| 입력 | 결과 | 이유 |
| --- | --- | --- |
| `Abcde` | 허용 | 숫자와 특수기호 없이도 조건 충족 |
| `ABCDE` | 허용 | 소문자는 필수 아님 |
| `aB1!_` | 허용 | 소문자로 시작해도 대문자를 포함하면 허용 |
| `abc1!` | 거부 | 대문자 없음 |
| `1Abc!` | 거부 | 숫자로 시작 |
| `_Abc1` | 거부 | 특수기호로 시작 |
| `Abc1@` | 거부 | 허용하지 않는 특수기호 |
| `Ab1!` | 거부 | 5자 미만 |
| `A12345678901234567890` | 거부 | 20자 초과 |
| `Ab 가1` | 거부 | 공백과 한글 포함 |

## 적용 후 확인

프로젝트의 기존 빌드 방식과 wrapper를 사용해 컴파일을 확인한다. 예를 들어 Gradle은 `compileJava`, Maven은 `compile`을 사용한다. 기존 검증 테스트가 있다면 관련 테스트를 실행한다. 검증 동작을 확인할 때는 null, 빈 문자열, 공백, 길이 경계(4·5·20·21자), 대문자 누락, 시작 문자, 허용 문자 밖의 입력을 확인한다.

어노테이션 적용과 요청 시 검증 실행은 별개다. 실제 요청 검증까지 요청받았다면 입력 경로의 `@Valid` 또는 `@Validated` 등 기존 검증 실행 방식도 확인한다.
